## 2. Schreibkosten des Suchindex (Review-Befund K1)

Der erste Entwurf hielt den FTS5-Index mit Triggern nach, die Zeilen über die nicht indizierten Spalten `kind`,
`item_id`, `ref_id` suchten: das Server-Review mass 34 ms je Ereignis bei 300'000 Indexzeilen (ein Vollscan der
Indextabelle). Seit `360036f` liegen die Texte in der gewöhnlichen Tabelle `search_docs` (eindeutiger Index über
`kind, ref_id, item_id`, Index über `item_id`), und `search_index` ist eine FTS5-Tabelle mit externem Inhalt, die per
Rowid nachgeführt wird; UPDATE-Trigger feuern nur, wenn sich ein Text ändert. Gemessen mit einem Go-Test gegen eine
frische Datenbank mit 100'000 Titeln, 200'000 Texten, 5'000 Personen und 50'000 Rollen (350'000 Indexzeilen), je
1000 Anweisungen:

| Ereignis | Zeit je Anweisung |
|---|---|
| Titel eines Items geändert | 0.19 ms |
| Titel unverändert gesetzt (z. B. Feed-Update) | 0.03 ms |
| Text (`item_texts`) per Upsert geändert | 0.18 ms |
| Rolle gelöscht | 0.22 ms |
| Person umbenannt | 0.49 ms |
| Titel gelöscht | 0.78 ms |

Ein Podcast-Abruf mit 2'000 bekannten, unveränderten Episoden kostet damit im Index Millisekunden statt Minuten. Die
FTS5-Integritätsprüfung (`INSERT INTO search_index(search_index) VALUES('integrity-check')`) ist im Migrationstest
nach dem Rückfüllen und nach den Triggerläufen grün.
